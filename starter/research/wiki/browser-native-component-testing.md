# Browser-native component testing

## Current synthesis

Vitest Browser Mode runs component tests in a real browser while keeping the focused scope and fast feedback of a unit-style test. The sources present this as the middle of a testing strategy. Component tests cover UI behavior and variations in isolation. End-to-end tests retain the critical journeys that need the whole application, including server rendering and routing behavior.

This model matters because browser behavior is part of the system under test. A DOM emulator cannot provide every browser API or match every browser constraint. Browser Mode removes that mismatch without requiring every interaction test to pay the setup and execution cost of a complete end-to-end journey.

The main distinction is where the test code runs and what the test treats as its unit. Vitest Browser Mode compiles the test suite as a small application and runs each test file in the browser. Playwright's test runner runs the test in Node.js and controls a browser page. Playwright Component Testing narrows the scope to components, but its Node.js test process must send a representation of the component to the browser for rendering.

Vitest's `page` API hides the selected automation provider. A suite can use Playwright or WebdriverIO without changing its browser test API. That abstraction is narrower than Playwright's full browser-automation API.

The Vitest 4.1.11 documentation supplies the primary reference that the earlier sources lacked. Vitest requires a provider. The docs reserve the `preview` provider for inspecting tests because it simulates events. They recommend Playwright or WebdriverIO for local runs and continuous integration. Playwright is the starting recommendation when provider-level parallel execution matters.

The current API is built around composable locators, provider-backed interactions, and retried `expect.element` assertions. Browser tests can also cross into the Vitest server through the Commands API when work must run in Node.js. This boundary preserves browser execution for test and application code without pretending that Playwright's server-side `page` object exists in the browser.

The official documentation also expands Browser Mode beyond interaction tests. It includes experimental accessibility-tree snapshots, experimental screenshot comparison, multiple browser instances, Playwright traces, and maintained renderer packages for Vue, React, and Svelte. These capabilities support the talk's middle-layer argument, but their provider limits and experimental labels belong in the story.

Running the test in a browser does not guarantee that every interaction uses browser automation. Younes calls a test that queries the DOM and dispatches events inside the browser "partial browser mode." He calls a test that uses Vitest's `userEvent` adapter or `page` locators "full browser mode." These are the speaker's terms, not established Vitest API names. In the second path, Vitest sends the action to the provider. Playwright can then reject a click when another element covers the target.

Alexander Opalic's Vue 3 case study pushes this middle layer further. His project uses browser integration tests as the base of the suite, with smaller groups of composable unit tests, accessibility checks, and visual snapshots. The strategy depends on application structure. Pure logic lives in composables, while browser tests render real Vue components with the router and store. Tests replace only external boundaries such as APIs and browser storage.

- Component tests render UI with supplied data and avoid unrelated application dependencies. The speakers recommend component tests for variations and end-to-end tests for critical paths. [The comparison runs from 07:00 through 11:30.](../raw/2024-09-13-use-vitest-with-browser-mode.md)
- Vitest runs the test file in the browser. Playwright end-to-end tests run their test code in Node.js and control a browser. Browser Mode does not replace Playwright's end-to-end test runner. [The distinction appears at 33:30.](../raw/2024-09-13-use-vitest-with-browser-mode.md)
- Zakharchenko defines the practical split by test unit. Vitest Browser Mode renders an isolated component in the browser. Playwright end-to-end tests treat the application page and complete user interactions as their unit. [The article compares each tool's purpose.](../raw/2025-11-12-vitest-browser-mode-vs-playwright.md)
- Vitest Browser Mode runs the test file and application code in the browser. Node.js-only work remains on Vitest's orchestration server and enters the test through the Commands API. [The article explains the test environment.](../raw/2025-11-12-vitest-browser-mode-vs-playwright.md)
- Playwright Component Testing runs the test file in Node.js and sends a serialized representation of the component to the browser. The article argues that this architecture makes it less direct than calling a framework renderer inside a browser test. [The article compares component rendering.](../raw/2025-11-12-vitest-browser-mode-vs-playwright.md)
- Vitest's `page` API stays the same when a suite switches between Playwright and WebdriverIO providers. The API intentionally exposes fewer browser-automation features than Playwright. [The article describes the provider abstraction and its limit.](../raw/2025-11-12-vitest-browser-mode-vs-playwright.md)
- Younes demonstrates a CSS regression that fixes a card's height and clips its overflow. A click through Testing Library's `userEvent` passes even though the button is no longer usable. Changing the import to Vitest's `userEvent` adapter makes the test fail because Playwright reports that another element intercepts the click. This is one controlled example of actionability checks catching a false negative. [The demonstration runs from 20:35 through 23:16.](../raw/2026-02-12-test-angular-components-like-a-real-user.md)
- The video separates browser execution from provider-controlled interaction. In the speaker's "partial" path, the browser loads and runs the test while the test queries and changes the DOM directly. In the "full" path, Vitest resolves the target and sends the action through its server to the browser provider. [The sequence diagrams run from 23:16 through 25:46.](../raw/2026-02-12-test-angular-components-like-a-real-user.md)
- Vitest's `page` queries return locators instead of querying the DOM immediately. The test can reuse a locator for actions and `expect.element` assertions. Those assertions retry until they pass or time out, while a locator that matches more than one target causes an action to fail. [The migration to locators runs from 26:36 through 32:28.](../raw/2026-02-12-test-angular-components-like-a-real-user.md)
- With the Playwright provider, the demonstration records a trace on the first retry and exposes it through the Vitest HTML report. - The proposed migration path has three independent steps. A suite can move to Vitest, enable Browser Mode for selected tests, and adopt Vitest's provider-backed interaction APIs when new tests are written or old tests are fixed. - The locator API follows Testing Library's semantic-query approach and draws its locator behavior from Playwright. Retriable `expect.element` assertions wait for browser state instead of checking once. [The API discussion starts at 23:30.](../raw/2024-09-13-use-vitest-with-browser-mode.md)

- Vitest locators are composable objects rather than resolved DOM elements. This lets Vitest retry interactions and `expect.element` assertions as the rendered page changes. The locator guide prefers roles and accessible names for interactive elements. - Browser test code cannot access Playwright's server-side `page` object. Vitest exposes a browser-side `page` abstraction and uses the Commands API for provider-specific or Node.js work. - The Vue renderer returns built-in Vitest locators and automatically cleans rendered components between tests. The guide recommends component-sized captures, explicit viewports, controlled animations and dynamic content, proportional pixel thresholds, and a consistent environment for reference ownership. - Browser instances can cover Chromium, Firefox, and WebKit while sharing one Vite server. [The pinned official documentation includes the multiple-setups guide.](../raw/2026-08-18-vitest-4-1-11-browser-mode-documentation.md)
- Playwright-provider runs can produce traces for every test, retries, or failures. Vitest groups interactions and `expect.element` assertions by source location, and custom `page.mark` or locator markers can label higher-level flows. [The pinned official documentation includes the trace-view guide.](../raw/2026-08-18-vitest-4-1-11-browser-mode-documentation.md)
- Browser Mode replaces native thread-blocking dialogs because `alert` and `confirm` would stop Vitest from communicating with the page. Native browser ESM also prevents `vi.spyOn` from patching an imported module namespace. The documented replacement is `vi.mock(path, { spy: true })`. ## Tensions and open questions

- The recording uses Vitest 2.1 on its release day. Treat its setup details and API names as historical when the Vitest 4.1.11 documentation differs.
- The live demo exposes rough edges in the new release. The generated example, `describe` block, file upload, and coverage flow each produce a problem. These failures are useful evidence for honest trade-offs, but they do not establish current defects.
- The source claims that a browser component suite can run far more cases than an end-to-end suite in the same time. The talk still needs a current benchmark before it presents a numeric comparison.
- The wiki now has the Vitest 4.1.11 primary documentation for provider setup, framework renderers, locators, cleanup, traces, accessibility snapshots, and screenshots. The talk still needs a current working example that proves the subset used on stage.
- The official docs contain a maturity conflict. The component-testing guide recommends Browser Mode for component testing and continuous integration. The "Why Browser Mode" page still calls the feature early-stage and recommends augmenting it with a standalone browser runner. The talk should avoid treating either sentence as a single current product position until maintainers reconcile the pages.
- Both ARIA snapshots and screenshot assertions carry experimental labels. Their presence in Vitest 4.1.11 establishes availability, not a stable long-term API contract.
- The 2025 demonstration exposed beta-era problems in the browser UI. Autosave could race with the test runner, the aggregate duration counter ignored parallel execution, and the canvas layout scaled poorly on smaller monitors. These observations do not establish current defects.
- Visual snapshots make otherwise awkward rendering states testable, but a failed image does not explain the behavioral cause. The talk needs a rule for when a screenshot earns its maintenance cost over a semantic assertion.
- Opalic's project reports Browser Mode as four times faster than JSDOM, while the earlier sources make only broader speed and feedback-loop claims. The talk needs a reproducible benchmark that controls configuration, concurrency, setup work, and failing tests before it repeats the multiplier.
- The article treats end-to-end tests as full-stack tests with no mocks and recommends browser integration tests for most Vue flows. The other sources retain end-to-end tests for critical application journeys. The talk must define where mocked browser integration stops and full-system proof begins.
- The proposed 70 percent integration-test distribution reflects one local-first Vue application. The talk still needs evidence that the ratio transfers to applications with server rendering, many backend contracts, or cross-service workflows.
- Zakharchenko calls JSDOM and Happy DOM obsolete for component tests. The article gives an architectural argument, not comparative data. The talk needs evidence before it repeats that broad conclusion.
- The article's comparison of Playwright Component Testing depends on implementation details from a pinned React adapter revision. The talk should confirm that the current adapter still uses the same serialization boundary before presenting it as current behavior.
- "Partial browser mode" and "full browser mode" explain an important difference, but they are labels introduced by the speaker. The talk must either define them as local terms or replace them with official Vitest terminology.
- The covered-button example proves that provider-backed actionability catches one class of false negative. It does not show how often direct DOM interaction misses defects across a real suite.
- The current primary docs confirm the trace, retry, and headless options shown in the February 2026 video. The Angular CLI, Nx, and Analog integration steps still need a current source before the talk presents them as setup guidance.
